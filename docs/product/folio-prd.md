## 1. 执行摘要

### 1.1 一句话定位

> **Folio 记得。然后帮你也记得。**

Folio 是一个账号制的云端个人阅读记忆产品。它接住用户主动选择的高价值内容，提炼有出处的洞察，在适当时间通过 Echo 帮助用户主动回忆，并在用户真正需要时通过 Ask 用证据调用这些知识。

### 1.2 核心问题

用户缺少的不是另一个保存入口，而是保存之后的完整知识转化链路：

```text
存了，但没有读
→ 读了，但没有记住
→ 记得看过，但无法找到
→ 找到内容，但无法快速形成可信结论
```

Folio 要解决的是：

> 如何把用户主动选择的内容，转化为以后能够记起、解释、验证和使用的个人知识。

### 1.3 核心产品闭环

以下描述长期闭环，能力按阶段启用。M3 首发先兑现“保存 → 阅读 → 高亮/笔记 → 搜索找回 → 导出”；AI 在 M4 增强理解，Echo 进入后续实验。

```text
存：低摩擦提交高价值内容
 ↓
解：提炼核心洞察并保留证据
 ↓
记：通过 Echo 主动回忆
 ↓
用：通过 Ask 获得有来源的回答
 ↓
反馈：真实使用让用户继续保存更高价值的内容
```

对用户的品牌表达保持为三个动词：**存 → 记 → 用**。“解”是系统内部完成的必要处理，不增加用户心智负担。

### 1.4 核心价值单位

Folio 的价值单位不是文章数量，而是：

> 一条有出处、被用户记住，并能在真实场景中再次调用的洞察。

### 1.5 分阶段验证逻辑

1. **Phase 1 / M1｜可靠收藏**：真实登录、分享或粘贴链接、正文阅读和删除；达到当期验收后即可小范围 TestFlight。
2. **Phase 2A / M2—M3｜阅读记录 MVP**：高亮、轻量笔记、关键词搜索、同步和最小 Markdown 导出形成可独立使用的闭环。M3 达标即可作为 App Store 1.0 候选。
3. **Phase 2B / M4｜当前文章 AI**：有依据洞察、当前文章/选中文字 Ask；稳定时可随 M3 发布，否则作为首个功能更新，不阻塞 M3。
4. **Phase 3｜Echo 留存实验**：不进入本轮开发；全资料库 Ask 也单独留在机会池，不与 Echo 绑定排期。

收藏数量不等于价值验证。M3 观察用户是否真实阅读、留下记录并再次找回；M4 再验证 AI 的增量价值，不用 AI 指标阻挡阅读闭环上线。

## 2. 研究基础与产品假设

### 2.1 当前证据状态

产品尚处于需求验证阶段。除本文件中的“已确认产品决策”外，关于用户规模、使用频率、留存、付费意愿和行为效果的判断均为待验证假设，不作为既成事实。

禁止在产品传播或内部决策中，将未经研究验证的假设描述为“用户普遍需要”或“市场已经证明”。

### 2.2 核心假设

| 编号 | 假设 | 风险 | 验证方式 | 通过标准 |
|---|---|---|---|---|
| HYP-001 | 高频阅读者存在明显的“收藏后遗忘”问题 | 高 | 12—15 名问题访谈 + 收藏库回溯 | ≥ 60% 核心样本能提供近一个月真实案例 |
| HYP-002 | 用户愿意把外部内容上传到个人云端资料库 | 高 | 隐私概念测试 + 可用性测试 | ≥ 70% 核心样本愿意提交非敏感工作资料 |
| HYP-003 | 结构化洞察比普通摘要更能解释“为什么值得保存” | 中 | 盲测对比 | 洞察方案偏好率 ≥ 65% |
| HYP-004 | 10—15 秒的主动回忆能够提供可感知价值 | 高 | 7 日 Echo 原型测试 | ≥ 40% 被展示任务完成；≥ 50% 完成者愿意继续 |
| HYP-005 | 有来源、会拒答的 Ask 比通用聊天更可信 | 高 | 答案信任测试 | 来源版信任评分显著高于无来源版 |
| HYP-006 | 用户愿意为高频 Echo、Ask 和云端容量付费 | 高 | Van Westendorp + 付费墙原型 | 年费候选区间存在可接受交集 |

### 2.3 Phase 0 用户研究计划

#### 样本

- 12—15 名核心目标用户；
- 每周主动保存至少 5 条内容；
- 覆盖产品、技术、设计、研究、投资或内容创作；
- 至少使用过一种书签、稍后读、笔记或 PKM 工具。

#### 研究任务

研究按阶段开展：收藏、云端信任与阅读记录先验证；AI 对比安排在 M4 前，Echo 七日实验安排在 Phase 3 前。后两项不阻塞 M1 或 M3。

1. 回溯最近 30 天真实保存内容和后续使用情况；
2. 观察一次从外部 App 保存内容的完整流程；
3. 测试“结构化洞察”与普通摘要的理解差异；
4. 连续 7 天体验 Echo 原型；
5. 比较有来源 Ask 与无来源 AI 回答的信任程度；
6. 测试账号、云端存储和数据删除说明是否可理解；
7. 访谈付费意愿和容量预期。

#### 研究输出

- 问题证据表；
- 用户分群和优先级结论；
- 核心流程可用性问题；
- 假设通过、修改或否决记录；
- MVP 范围调整建议。

## 3. 产品目标与边界

### 3.1 商业目标

验证一个面向个人知识工作者的订阅产品，能否通过“记忆收益”和“可信调用”形成长期留存与付费，而不是依赖一次性 AI 摘要或无限增长的收藏库存。

### 3.2 用户结果目标

以下结果随对应能力启用后验证，不要求 M3 用户体验尚未上线的 AI 或 Echo：

1. 我提交的内容被可靠保存，不需要手工整理；
2. Folio 能说清每篇内容最值得记住的是什么；
3. 我记住了一部分过去会忘记的观点；
4. 我能用自然语言找回知识，并核对原始依据；
5. 我可以在不同设备访问并管理自己的资料，也能清晰删除内容或账号。

### 3.3 分阶段产品目标

| 编号 | 阶段 | 目标 | 对应验证 |
|---|---|---|---|
| OBJ-001 | Phase 1 | 建立从账号登录到云端保存成功的可靠采集链路 | 激活与保存成功率 |
| OBJ-002 | Phase 1 | 建立账号、云端容量和删除的信任基础 | 多端一致性与删除正确性 |
| OBJ-003 | Phase 2A / M2—M3 | 让用户阅读、高亮、记录、找回并带走自己的积累 | 高亮/笔记使用率、搜索打开率和导出成功率 |
| OBJ-004 | Phase 2B / M4 | 建立有依据洞察与当前文章问答 | 洞察准确性、引用准确率与拒答正确率 |
| OBJ-005 | Phase 3 | 建立轻量、无压力的主动回忆闭环 | Echo 完成率与延迟回忆率 |

App Store 1.0 不包含：

- 离线保存、离线阅读和离线搜索；

- 团队协作、评论和权限空间；

- 语音输入；
- 通用 AI 聊天；
- 独立的 Spark、Learn 或类似功能模块；
- 阅读任务、未读压力和连续签到惩罚；
- 批量迁移其他产品历史数据。

## 4. 目标用户与使用场景

### 4.1 第一优先用户

需要持续阅读外部内容，并在工作、研究或创作中复用信息的个人知识工作者。

典型职业包括：

- 产品经理、工程师和设计师；
- 行业研究、投资研究和咨询从业者；
- 作者、内容创作者和独立开发者；
- 研究生、教师和持续学习者。

### 4.2 行为筛选条件

第一优先用户至少满足其中三项：

- 每周主动保存 5 条以上内容；
- 内容来源跨越浏览器、微信、X、微博、博客或截图；
- 曾经出现“我记得看过，但找不到”的情况；
- 使用过书签、稍后读、笔记或 PKM 工具；
- 需要在会议、写作、研究或决策中引用过去读过的信息；
- 在意 AI 回答来源、云端隐私和数据删除能力。

### 4.3 非目标用户

- 只需要同步浏览器书签的轻度用户；
- 需要多人知识库、权限管理和协作流程的团队；
- 以长篇写作和复杂笔记组织为核心需求的用户；
- 以信息流消费、RSS 阅读或热点发现为核心需求的用户。

### 4.4 Jobs to Be Done

| 编号 | 场景 | Job |
|---|---|---|
| JTBD-001 | 看到有价值内容时 | 我希望用最少操作可靠提交，然后立即回到当前任务，不需要先分类整理 |
| JTBD-002 | 内容即将被遗忘时 | 我希望系统用一个简短问题唤醒记忆，而不是再次推送全文 |
| JTBD-003 | 需要过去读过的知识时 | M3 能搜索自己的记录并返回原文；M4 能针对当前文章提问并核对依据；长期再支持全库自然语言调用 |
| JTBD-004 | 更换设备或长期积累时 | 我希望登录账号后看到同一份资料，并能清晰删除内容或账号 |

### 4.5 核心使用场景

#### SCN-001：外部内容保存

用户在 Safari、微信、X、微博或其他 App 中看到值得保留的内容，通过系统分享面板提交到 Folio。服务端确认接收后用户离开，后续抽取和理解在云端完成。

#### SCN-002：每日短时回忆

用户打开 Folio 或响应通知，看到一张 Echo。用户先回忆、再揭晓，查看证据后选择“记得”或“忘了”，整个过程控制在 10—15 秒。

#### SCN-003：阅读中调用知识

M3 用户通过关键词搜索找回正文和记录；M4 用户在当前文章或选中文字范围提问，展开证据并返回原文。跨资料库模糊提问属于后续候选场景。

#### SCN-004：跨设备继续使用

用户在新设备登录同一账号，看到一致的内容状态、Echo 调度和使用权益，不进行本地数据库迁移。

#### SCN-005：账号与数据删除

用户删除单条内容、清空资料库或删除账号，并获得清晰的影响范围、撤销期和完成说明。

## 5. 产品原则

1. **接收成功优先**：只有服务端确认接收后，才能告诉用户“已保存”。
2. **先提交，再处理**：用户不等待正文抽取和 AI 理解。
3. **默认完成选择**：系统负责主题、证据、回顾时机和问答来源选择。
4. **主动回忆优于被动重读**：Echo 必须先提问，再展示答案。
5. **证据优于表达**：回答宁可短，也必须能回到原始依据。
6. **不知道也是答案**：证据不足时明确拒答，不用模型常识补齐。
7. **云端单一事实源**：客户端不维护需要合并的持久化内容资料库。
8. **不制造知识债务**：不使用未读数量、清零任务和签到惩罚。
9. **数据可控是云端信任的一部分**：用户已有内容始终可访问，并能清晰删除内容或账号。
10. **每项功能必须服务于“存、记、用”中的至少一步**。

|---|---|---|
| 账号与会话 | AUTH-001—006 | 建立和恢复自己的资料库 |
| 分享与粘贴链接 | CAP-001、CAP-004—010 | 云端确认后可离开，失败可恢复 |
| 正文与来源 | INS-001、LIB-001—007 | 阅读受支持来源内容；仅 URL 记录不冒充正文完成 |
| 数据与容量 | DATA-001—006、BILL-002—004、BILL-008 | 数据隔离、可删除、成本可控 |

来源先覆盖 TikHub 已核实的微信文章和 X 推文接口；生产支持承诺须通过 CAPT-03 样本验收。其他公开网页先保留 URL，并明确正文暂不可用；不静默接入未经选择的第二家采集服务。系统分享扩展是 iOS 入口，不是浏览器插件。

### 6.3 Phase 2｜阅读记录先上线，AI 后增强

| 子阶段 | 能力域 | 需求编号 | 用户价值 |
|---|---|---|---|
| Phase 2A | 高亮与轻量笔记 | NOTE-001—005 | 留下自己的重点和想法 |
| Phase 2A | 关键词搜索 | LIB-008 | 搜标题、来源、正文、高亮和笔记并定位 |
| Phase 2A | 最小导出 | EXP-001—002 | 带走标注与来源，不锁住个人记录 |
| Phase 2B | 洞察与证据 | INS-002—005 | 理解文章核心观点并核对 |
| Phase 2B | 当前文章 Ask | ASK-001—008、NOTE-006 | 在明确的文章/选区范围内提问 |
| Phase 2B | AI 额度 | BILL-007 | 结果可用才扣额度，失败不影响原文 |

Phase 2A 达标即可公开发布；Phase 2B 的评测门槛只约束 AI 的启用。收费能力 BILL-001/005/006 仅在正式收费前执行，不能把没有付费入口的试用误称为订阅已完成。

### 6.4 Phase 3｜Echo 留存

保留 ECHO-001—006，当前为机会池；首轮实验只包含先回忆、后揭晓、记得/忘了和简单间隔。没有 Echo 不影响 M1—M4 的放行。

### 6.5 后续候选范围

- 全资料库 Ask、跨文章综合与语义搜索；
- iPad、macOS 或 Web 客户端；
- 完整正文/媒体导出、其他工具导入与双向同步；
- 多色高亮、标签、复杂笔记格式；
- 截图 OCR、文字片段、TTS、离线阅读、RSS；
- Echo、观点关联、Widget 和更精细回忆算法。

### 6.6 阶段内优先级规则

每个阶段先完成已承诺的用户动作和数据保护，再扩大范围。顺序为：账号与可靠接收 → 原文/标注完整性 → 阅读记录与找回 → 数据可带走 → 当期 AI 证据质量 → 商业化与其他增强。M3 不因后续 AI 或 Echo 推迟。

## 7. 产品体验架构

本文档不规定标签栏数量和具体视觉布局，只规定用户必须能够完成的核心任务。

### 7.1 三种使用情境

#### 捕获情境

用户只想快速提交内容。主要入口位于系统分享面板，成功标准是服务端确认接收，而不是 AI 已经处理完成。

#### 回访情境

回访入口随产品阶段演进：Phase 1 优先帮助用户找到和继续阅读已保存内容；Phase 2A 优先帮助阅读、记录和找回，Phase 2B 提供洞察；Phase 3 启用后，优先呈现一项值得完成的 Echo。Echo 不应被当作多个统计卡片中的一个模块。

#### 调用情境

M4 用户针对当前文章或选中文字寻求答案，回答、证据与原文必须构成连续链路。独立 Ask 入口也必须先有明确文章范围；不得开放全资料库检索或通用聊天。

### 7.2 核心产品对象

| 对象 | 产品含义 |
|---|---|
| Account | 用户身份、会话、权益和数据隔离边界 |
| Content | 用户提交的原始内容及处理状态 |
| Source | 原始 URL、正文位置、作者和发布时间等证据信息 |
| Insight | 可被记忆和调用的核心观点 |
| Echo Card | 围绕一条洞察生成的回忆问题和答案 |
| Recall Log | 一次 Echo 的揭晓、评价和时间记录 |
| Ask Query | 用户提出的问题 |
| Ask Answer | 结论、引用、证据和拒答状态 |
| Entitlement | Free / Pro 权益、容量和使用额度 |

### 7.3 内容生命周期

```text
submitting
→ accepted
→ extracting
→ ready（M1—M3 正文可用）
→ understanding → ready（M4 可选 AI，独立状态）

异常分支：
submitting → rejected
extracting / understanding → degraded
extracting / understanding → retryable_failed
任意可删除状态 → deleting → deleted
```

## 8. 核心用户流程

### 8.1 Phase 1 首次使用

```text
打开 App
→ 查看或跳过价值说明
→ Apple 登录或邮箱登录
→ 创建或加载云端资料库
→ 引导从外部 App 分享第一条内容
→ 服务端确认接收
→ 云端完成正文抽取
→ 用户在资料库中找到并在线阅读
```

Phase 1 Aha Moment：**“我在外部 App 保存后可以立即离开，内容已经可靠出现在资料库里。”**

Phase 2B / M4 启用后，第一条内容进一步展示核心洞察，形成第二个 Aha Moment：**“它抓住的正是我保存这篇内容的原因。”**

### 8.2 日常保存

```text
在外部 App 看到内容
→ 分享到 Folio
→ 校验会话和容量
→ 向云端提交
→ 收到内容 ID 和接收确认
→ 用户返回原任务
→ 云端异步处理
```

无网络、会话失效、容量不足或上传失败时必须显示“尚未保存”，不得建立用户不可见的本地待上传队列。

### 8.3 Phase 3 第一次 Echo

```text
存在可回忆洞察
→ 用户打开 App
→ 看到一个回忆问题
→ 在心中作答
→ 点击揭晓
→ 查看答案和证据
→ 选择“记得”或“忘了”
→ 服务端安排下次回顾
→ 完成后再请求通知权限
```

记忆 Aha Moment：**“上次没有记住，这次我能说出来了。”**

### 8.4 Phase 2B / M4 当前文章 Ask

```text
用户在当前文章或选中文字范围提出问题
→ 检索该范围内的正文证据与已启用的个人记录
→ 判断证据是否充足
→ 生成带行内引用的短答案，或明确拒答
→ 用户展开证据
→ 返回原文核对
```

### 8.5 账号删除

```text
用户发起账号删除
→ 查看删除范围和不可逆说明
→ 二次身份验证
→ 进入撤销期
→ 撤销期结束后删除在线数据
→ 按数据保留规则清理备份
→ 发送完成确认
```

## 9. 功能需求

### 9.1 账号与会话

| ID | 需求 | 阶段 | 验收摘要 |
|---|---|---:|---|
| AUTH-001 | 用户可通过 Sign in with Apple 创建或登录账号 | Phase 1 | 首次登录、重复登录和换机登录均返回同一账号 |
| AUTH-002 | 用户可通过邮箱验证码创建或登录账号 | Phase 1 | 验证码具备有效期、频率限制和错误次数限制 |
| AUTH-003 | 登录是资料库、保存、Echo 和 Ask 的前置条件 | Phase 1 | 未登录不得访问核心数据或提交内容 |
| AUTH-004 | 客户端安全保持会话，并在过期时刷新或重新认证 | Phase 1 | 会话失效不泄露数据，不误报提交成功 |
| AUTH-005 | 用户可查看并撤销已登录设备和会话 | Phase 1 | 被撤销设备下一次请求立即失效 |
| AUTH-006 | 退出登录只清理凭证和临时缓存，不删除云端内容 | Phase 1 | 重新登录后内容和历史完整恢复 |

#### AUTH-003 详细规则

- 前置条件：用户已完成身份验证；
- 未登录时允许访问：品牌说明、登录、隐私政策、服务条款和帮助；
- 未登录时禁止访问：资料库、阅读、Echo、Ask、数据管理和 Share Extension 提交；
- Share Extension 会话失效时，引导打开主 App 登录；
- 不提供“稍后登录”或匿名资料库。

### 9.2 内容采集

| ID | 需求 | 阶段 | 验收摘要 |
|---|---|---:|---|
| CAP-001 | 支持系统分享面板或 App 内粘贴 URL 收藏 | Phase 1 | 两个入口使用同一接收契约；返回云端内容 ID 后才显示成功 |
| CAP-002 | 支持在 App 内提交文字片段 | Phase 2 候选 | 保留原始文本和提交时间 |
| CAP-003 | 支持提交单张或多张截图 | Phase 2 候选 | 原图上传成功后才确认接收 |
| CAP-004 | 服务端接收与后续抽取、AI 处理解耦 | Phase 1 | 用户不等待抽取和 AI 即可离开 |
| CAP-005 | 对重复 URL 和重复请求进行幂等处理 | Phase 1 | 重试不产生重复资产，可打开已有内容 |
| CAP-006 | 展示可理解的内容处理状态 | Phase 1 | 用户能够区分已接收、处理中、部分完成和失败 |
| CAP-007 | 提交失败和处理失败提供不同恢复路径 | Phase 1 | 提交失败不显示成功；处理失败保留原始资产 |
| CAP-008 | 提交前校验账号容量和内容限制 | Phase 1 | 容量不足时不上传大文件，不误报成功 |
| CAP-009 | 建立首发来源能力矩阵和降级规则 | Phase 1 | 微信/X 先验证；其他网页仅保留 URL；每类来源明确完整/部分/仅 URL/拒绝，按来源统计 |
| CAP-010 | 服务端通过 TikHub 获取受支持来源内容 | Phase 1 | 密钥仅在服务端；异步采集、来源 ID 校验、超时/限流/余额失败可恢复；第三方成功响应不等于正文验收通过 |

#### CAP-001 主流程

- 用户角色：已登录用户；
- 前置条件：网络可用、会话有效、容量充足；
- 触发：用户在外部 App 中选择“分享到 Folio”；
- 输入：URL、来源 App、客户端请求 ID；
- 服务端输出：内容 ID、接收时间、初始处理状态；
- 成功反馈：显示“已保存”；
- 后续动作：服务端异步调用 TikHub 并归一化正文；M4 启用后再独立生成洞察。保存确认不等待 TikHub 完成。

#### CAP-001 异常流程

| 条件 | 产品结果 | 用户操作 |
|---|---|---|
| 无网络 | 显示“尚未保存，需要联网” | 在分享面板内重试或退出 |
| 会话失效 | 显示“请先重新登录” | 打开主 App 登录 |
| 容量不足 | 显示容量状态 | 删除内容或升级容量 |
| 请求超时 | 查询请求 ID 状态 | 已接收则显示成功；未知则允许安全重试 |
| 重复 URL | 返回已有内容 | 打开已有内容或取消 |
| 没有正文接口的公开 URL | 保留链接，标记“仅保存链接，正文暂不可用” | 打开原网页或删除 |
| 非 HTTP(S)、私有网络或无效 URL | 明确拒绝，不交给采集服务 | 修改链接 |

#### CAP-006 内容状态

| 状态 | 用户含义 | 可执行操作 |
|---|---|---|
| 正在提交 | 正在向云端发送 | 等待、取消 |
| 已接收 | 原始输入已由云端接收 | 打开、删除 |
| 等待处理 | 云端正在排队 | 刷新 |
| 处理中 | 正在抽取或理解 | 查看已有信息 |
| 已完成 | 当前阶段的正文或派生内容可用 | 阅读；使用当前阶段已开放能力 |
| 部分完成 | 原始内容可用，增强能力失败 | 阅读、重试增强 |
| 处理失败 | 当前无法继续处理 | 查看原因、重试、删除 |
| 已删除 | 已从在线资料库移除 | 撤销期内恢复 |

### 9.3 内容抽取与洞察

| ID | 需求 | 阶段 | 验收摘要 |
|---|---|---:|---|
| INS-001 | 保存原始输入、来源信息和可获得的正文 | Phase 1 | 抽取失败不影响原始 URL 资产 |
| INS-002 | 生成一句核心洞察和 2—5 条关键观点 | Phase 2B / M4 | 洞察不重复标题，关键观点覆盖核心内容 |
| INS-003 | 每条洞察和关键观点保留原文证据 | Phase 2B / M4 | 人工评测可定位到原文依据 |
| INS-004 | 用户可反馈“有用”或“不准确” | Phase 2B / M4 | 反馈进入质量分析，不直接篡改原文 |
| INS-005 | 支持安全重新处理内容 | Phase 2B / M4 | 新版本成功前保留上一个可用版本 |

#### INS-002 输出规范

每条可处理内容输出：

- 一句话核心洞察；
- 2—5 条关键观点；
- 主题和语义关键词；
- 来源、作者、发布时间和提交时间（可获得时）；
- 每条观点对应的证据位置；
- 内容语言；
- 处理版本和时间。

质量规则：

1. 核心洞察必须表达信息增量，不能只改写标题；
2. 不得补充原文没有表达的确定性结论；
3. 内容不足时输出“无法可靠提炼”，不生成虚假完整摘要；
4. 默认使用用户界面语言，专有名词保留原文；
5. 原始正文和 AI 派生内容必须区分展示。

|---|---|---:|---|
| LIB-001 | 资料库默认按最近提交时间展示 | Phase 1 | 支持分页，处理状态清晰 |
| LIB-002 | 支持按内容类型和处理状态筛选 | Phase 1 | 筛选可清除，不要求维护分类树 |
| LIB-003 | 在线阅读云端保存的原文及当前阶段已有的派生内容 | Phase 1 | 原网页失效时，已保存正文仍可在线访问 |
| LIB-004 | 支持删除和短期撤销 | Phase 1 | 删除在同账号所有设备生效 |
| LIB-005 | 网络不可用时明确说明在线能力不可用 | Phase 1 | 不把临时缓存包装为离线资料库 |
| LIB-006 | 提供稳定、可访问的基础在线阅读体验 | Phase 1 | 支持正文排版、Dynamic Type、VoiceOver、阅读位置恢复和返回原网页 |
| LIB-007 | 用户可报告单条内容的解析或展示问题 | Phase 1 | 可区分缺页、图片丢失、格式错误和来源打不开，并保留提交与重试状态 |
| LIB-008 | 支持搜索标题、来源、正文、高亮和笔记 | Phase 2A | 返回结果显示命中片段，可清除搜索并回到原文位置 |

资料库不提供：

- 文件夹树；
- 强制分类；
- 未读数量压力；
- 阅读任务；
- 本地下载管理。

### 9.5 高亮与轻量笔记

| ID | 需求 | 阶段 | 验收摘要 |
|---|---|---:|---|
| NOTE-001 | 用户可在已保存正文中选择文字并创建或取消高亮 | Phase 2A | P0 使用单一默认样式；刷新或换机后高亮仍对应原文 |
| NOTE-002 | 用户可为整篇内容或某条高亮添加、编辑和删除纯文本笔记 | Phase 2A | P0 不要求 Markdown、附件、双向链接或独立笔记文档 |
| NOTE-003 | 用户可集中查看一篇内容的高亮与笔记，并跳回对应原文 | Phase 2A | 每条记录显示原文摘录、用户笔记和创建时间 |
| NOTE-004 | 高亮与笔记在同账号设备间同步，正文重新处理时不得静默丢失 | Phase 2A | 无法重新定位时保留摘录并标记“原文位置已变化” |
| NOTE-005 | 搜索可命中用户高亮与笔记 | Phase 2A | 结果明确标记正文、高亮或笔记，并可跳回对应位置 |
| NOTE-006 | 当前文章 Ask 可使用该文章的高亮与笔记，明确区分原文和用户记录 | Phase 2B / M4 | 不检索其他文章的笔记；引用标记“原文”或“我的笔记”，不得混写来源 |

P0 高亮与笔记保持轻量：单一高亮样式、纯文本短笔记、按文章查看。多颜色、标签体系、独立笔记库和复杂编辑器进入 P1 或更晚阶段。

### 9.6 Echo 主动回忆

| ID | 需求 | 阶段 | 验收摘要 |
|---|---|---:|---|
| ECHO-001 | 基于核心洞察生成可独立回答的回忆问题 | Phase 3 | 问题不直接暴露答案，有明确证据 |
| ECHO-002 | 用户必须先看到问题，再主动揭晓答案 | Phase 3 | 揭晓前不展示答案或关键提示 |
| ECHO-003 | 用户可选择“记得”或“忘了” | Phase 3 | 反馈成功提交后才更新状态 |
| ECHO-004 | 服务端根据反馈安排下次回顾 | Phase 3 | “忘了”缩短间隔，“记得”延长间隔 |
| ECHO-005 | App 内 Echo 不依赖通知权限 | Phase 3 | 拒绝通知后仍可完成 Echo |
| ECHO-006 | 完成首次 Echo 后再请求通知权限 | Phase 3 | onboarding 不提前请求通知 |

#### Echo 卡片结构

1. 来源标题或主题；
2. 一个回忆问题；
3. “揭晓”操作；
4. 简洁答案；
5. 原文证据和打开原文入口；
6. “记得 / 忘了”反馈。

#### Echo 调度规则

- 第一张卡片在产生可用洞察后的 1—3 天内出现；
- 一次默认只展示一张卡片；
- 用户可主动继续下一张，也可结束；
- 不使用连续签到惩罚；
- Phase 3 首版使用 1、3、7、14 天的简单可解释间隔；
- 是否升级复杂算法，根据 Phase 3 行为数据决定。

### 9.7 Source-backed Ask

| ID | 需求 | 阶段 | 验收摘要 |
|---|---|---:|---|
| ASK-001 | 用户可提交自然语言问题 | Phase 2B | 输入为空、过长或违规时有明确反馈 |
| ASK-002 | 在当前文章或选中文字范围自动选择证据 | Phase 2B / M4 | 文章 ID 与范围明确；用户无需手工挑证据段落；不跨文章检索 |
| ASK-003 | 回答直接、简洁，并包含行内引用 | Phase 2B | 引用编号与来源一一对应 |
| ASK-004 | 用户可展开证据并打开原文 | Phase 2B | 引用可定位到对应内容或最接近位置 |
| ASK-005 | 证据不足时明确拒答 | Phase 2B | 不用通用模型知识补齐缺失事实 |
| ASK-006 | 删除内容后不得继续检索或引用 | Phase 2B | 删除完成后相关引用立即失效 |
| ASK-007 | 明确展示 Ask 使用额度和恢复时间 | Phase 2B | 达到额度后不丢失已生成回答 |
| ASK-008 | 用户可针对选中文字或当前文章提问 | Phase 2B / M4 | 持续显示两种范围；由选区扩大到当前文章需用户操作；不提供“全部资料”选项 |

#### Ask 结果状态

| 状态 | 定义 | 产品表现 |
|---|---|---|
| answered | 有足够证据形成回答 | 短答案、行内引用、来源列表 |
| insufficient_evidence | 资料不足或相关性不够 | 说明缺少什么，并建议收窄问题 |
| processing | 相关内容尚在处理 | 告知可稍后重试 |
| quota_exceeded | 当前额度已用完 | 显示恢复时间；仅收费能力已启用时显示升级入口 |
| error | 服务暂时失败 | 保留问题，允许重试 |

#### Ask 引用规则

1. 每个确定性事实必须由实际参与回答的来源支撑；
2. M4 只使用当前文章/选区及其明确标记的个人记录；跨文章综合不启用；
3. 不展示未被回答使用的“装饰性来源”；
4. 流式回答不得先生成无证据结论再补引用；
5. 如果证据相互冲突，回答必须呈现冲突，而不是选择一个看似确定的结论；
6. 回答必须区分原文事实、用户笔记和基于当前文章的解释，不把解释写成原文直接结论。

## 11. 体验与内容规范

### 11.1 产品气质

- 安静、克制、原生；
- 用层级和留白表达重点，不用卡片数量表达功能丰富；
- 阅读、高亮和轻量笔记是日常体验中心，Ask 是有证据的调用能力，Echo 在后续验证长期记忆价值；
- 不使用未读红点、知识焦虑和签到惩罚促进活跃；
- 状态反馈明确，但避免持续打扰。

### 11.2 文案原则

1. 明确说明结果，不使用模糊成功文案；
2. 区分“尚未保存”和“已保存但处理失败”；
3. 拒答说明证据边界，不使用“AI 出错了”掩盖资料不足；
4. 订阅提示说明用户获得什么，不制造数据丢失恐惧；
5. 删除和账号注销文案必须说明影响范围、撤销期和不可逆节点。

### 11.3 通知原则

- onboarding 不请求通知；
- 用户完成首次 Echo 后再解释通知价值；
- 通知用于提醒待回忆洞察，不用于推广和保存数量汇报；
- 用户拒绝通知后，核心 Echo 能力仍在 App 内可用；
- 默认频率克制，允许完全关闭。

### 14.1 商业原则

1. 账号注册、访问已有内容和删除不是付费墙；
2. 免费用户可体验当期核心动作：Phase 2A 阅读记录与导出，Phase 2B 再加入理解和问答，Phase 3 再加入记忆；
3. 付费点位于持续复利的频率、深度、云端容量和高级检索；
4. 不按每月保存篇数收费，以容量管理存储成本；
5. 订阅到期不删除、不隐藏、不锁定已有数据；
6. 超出 Free 容量时停止新增，但允许阅读、删除和重新降低用量。

### 14.2 定价假设

首轮年费候选区间：人民币 88—128 元。

该区间必须经过以下验证后才能确定：

- 目标用户付费意愿访谈；
- Free / Pro 权益理解测试；
- 云端存储和 AI 单位成本；
- TestFlight 真实用量分布；
- App Store 可用价格等级。

### 14.3 付费触发原则

- Phase 2 中，用户至少体验过一次洞察或 Ask 价值后再展示 AI 付费；Phase 3 的 Echo 付费提示只在用户完成首次 Echo 后出现；
- 容量不足提示说明当前用量和解决方案；
- Echo / Ask 达到额度时保留已有结果；
- 不使用“数据即将丢失”制造付费压力；
- 升级后权益应立即在所有设备生效。

## 16. 发布计划

### Phase 0 / M0：范围与技术准备

- 完成 PLAN-02 与 BASE-01；生产骨架和数据契约由 BASE-02/03 实施。
- 核验 TikHub 凭证与来源样本、Apple 分发、托管、邮箱和存储条件；未就绪依赖有对应任务和处理节点。
- 问题访谈、样本采集与实现可以交错进行；HYP-003/005 的 AI 评测在 M4 前，HYP-004 的 Echo 实验在 Phase 3 前，不阻塞 M1/M3。

### Phase 1 / M1：收藏阅读 TestFlight

范围：账号、粘贴 URL、真实系统分享扩展、TikHub 异步采集、来源能力分级、状态/重试、在线正文阅读与进度、内容/账号删除。

退出条件：

- 真实来源从分享到再次打开的链路通过；仅 URL 记录清楚说明正文不可用；
- 无网络、超时、重复、容量不足和采集预算暂停不误报成功；
- 接收后原始输入不丢，跨账号隔离、删除、恢复和分发检查通过；
- 达标即开放小范围 TestFlight，不等待标注、AI 或 Echo。

### Phase 2A / M2：高亮与笔记试用

范围：单一高亮、文章/高亮纯文本笔记、标注列表、原文定位和跨会话恢复。

退出条件：选词→高亮→笔记→重登恢复→回到原文可完成；正文重处理不能静默丢记录；中文键盘不阻断编辑与返回。达标后邀请同一批用户真实记录，不等待搜索和 AI 全部完成。

### Phase 2A / M3：阅读记录 MVP / App Store 1.0 候选

范围：在 M1/M2 基础上补齐标题/来源/正文/高亮/笔记关键词搜索，命中定位，单篇与批量最小 Markdown 导出、容量与处理预算说明。

发布条件：

- 用户可独立完成收藏→阅读→高亮/笔记→搜索→原文→导出；
- 数据完整性、账号隔离、删除与恢复、当期性能/无障碍/国际化门槛通过；
- 实际分发、隐私说明、支持入口、监控与备份恢复记录齐全；
- 本轮免费试用不等待订阅功能；若转为收费，必须先完成购买/恢复/到期/退款权益验收；
- 真实试用问题有修复或明确处理结论；严重缺陷未解决不放行。

当前文章 AI 未达到质量门槛时不启用，不阻塞 M3；不得宣传尚未交付的 AI/Echo 能力。M3 不验证 AI 或长期记忆收益已经成立。

### Phase 2B / M4：当前文章 AI 更新

范围：一句洞察、关键观点、质量反馈、证据上下文；选中文字与当前文章两种 Ask 范围；明确拒答、实际消费记录与成本控制。

发布条件：

- 真实固定评测集的洞察准确性、引用与拒答达到当期门槛；
- 问题→答案→证据→原文连续可用，个人笔记与原文区分；
- 删除内容后不再引用；失败/取消/证据不足不扣用户 AI 额度；
- AI 故障不影响阅读、标注、搜索和导出；
- 该版本不提供全库 Ask、跨文章综合或 Echo。

如果 M4 在 M3 放行前已独立达标，可一起发布；否则作为后续功能更新。

### Phase 3：Echo 留存实验（本轮不开发）

保留核心洞察提问、先回忆后揭晓、原文证据、记得/忘了、简单间隔与通知。只有开展该实验时才应用 ECHO 验收和记忆收益指标；不纳入 M1—M4 的任务完成率。

## 17. MVP 优先级与开发待办

### 17.1 优先级定义

| 优先级 | 定义 | 当前处理方式 |
|---|---|---|
| P0 | 当前里程碑兑现用户动作或安全交付所必需 | M3 阅读闭环与 M4 AI 分别验收；不是所有 P0 都阻塞首次发布 |
| P1 | 能明显提高使用频率、阅读深度或数据信任，但缺失时 P0 闭环仍成立 | 进入 MVP 后首批候选，先验证再立项 |
| P2 | 有潜在价值，但依赖用户行为、内容规模或额外平台能力 | 保留机会，不承诺时间 |
| 暂不做 | 容易制造功能膨胀，且当前没有证据证明能加强核心闭环 | 不进入当前路线图 |

P0 功能必须是用户在界面中可以直接完成、能够解释“为什么要用 Folio”的动作。账号、安全、抽取、当期容量/成本和性能仍是 P0 交付条件，但单独列为交付底座，不再冒充用户功能。

### 17.2 状态规则

| 状态 | 含义 |
|---|---|
| `backlog` | 已识别的机会，尚未批准进入开发 |
| `todo` | 已批准进入当前范围，尚未开始生产实现 |
| `doing` | 已有明确负责人和在制实现 |
| `blocked` | 因外部依赖或未决决策无法继续，必须写明阻塞原因 |
| `done` | 生产实现、需求验收和必要测试均通过，并已记录可复查证据 |

状态更新规则：

- 每次变更状态必须同时更新“更新时间”和“完成证据 / 阻塞原因”；
- `done` 至少需要生产代码、关联需求验收、针对性测试，以及 commit、PR 或测试记录之一；

不等待后续里程碑才开始试用：M1 达标即可分发小范围 TestFlight；M2 邀请同一批用户真实高亮和记录；M3 达标后可公开发布。若 AI 已稳定可随 M3 发布，若未稳定则按 M4 更新。外部审核等待时间单独记录，不隐含在编码时间内。

关键路径：

```text
范围同步与技术摸底
→ 生产工程/云端/账号
→ 真实收藏与正文版本
→ 阅读与原文定位
→ 高亮和笔记持久化
→ 搜索定位、导出与发布验收
→ 当前文章 AI 与证据评测
```

AI 接口可在正文与证据契约稳定后准备，但单人执行优先完成当前里程碑，不同时打开多个大功能。

## 24. 技术摸底与实施基线（BASE-01）

核验日期：2026-09-06。本节交付技术选择、复用判断、接口文档核验和实施依赖；没有建立生产工程、调用付费 TikHub API、部署服务或验证 App Store Connect。`BASE-01 done` 只表示摸底完成。

### 24.1 生产工程与架构选择

| 层次 | 本轮选择 | 原因与实施边界 |
|---|---|---|
| iOS | 新建 `ios-app/`，SwiftUI、iOS 26+，主 App + Share Extension | 沿用 Demo 视觉组件；URLSession/async-await 请求真实后端；Keychain 保存凭证；App Group/Keychain Access Group 共享必要会话；不使用 SwiftData 持久化内容 |
| 服务端 | 新建 `backend/`，Go + Chi + pgx | 与历史代码栈接近；API 与 worker 使用同一代码库、不同进程入口；不恢复整套历史架构 |
| 数据与任务 | PostgreSQL 18，数据库事务任务表 | 一次事务写入内容、幂等键和采集任务后才确认接收；MVP 不引入 Redis/Asynq，避免数据库写入与队列入队之间丢任务 |
| 正文与图片 | 正文版本、段落、标注存 PostgreSQL；图片存 S3 兼容对象存储 | 正文采用规范化结构化块；图片保存失败标为部分完成；不依赖临时第三方图片链接保证长期阅读 |
| 采集 | TikHub，先接微信文章与 X 单条内容 | Folio 后端保存供应商密钥；按来源适配，客户端不直连；供应商结果经过完整性检查再入正文版本 |
| 搜索 | PostgreSQL `pg_trgm` + 转义后的 `ILIKE` | 先完成中文关键词子串匹配；一至两个字可能无法有效使用 trigram 索引，需账号范围、长度/频率限制和真实数据性能验证；暂不引入向量库 |
| 发布 | HTTPS API、worker、PostgreSQL、对象存储的最小拓扑 | 具体托管服务和域名待确认；不把已知 SSH 服务器自动当作部署授权或既定目标 |

任务 worker 用事务领取到期任务，可使用 `FOR UPDATE SKIP LOCKED`，提交领取事务后再发起外部请求，避免持锁等待供应商。设置租约、重启回收、退避、最大尝试次数和失败记录。租约解决进程恢复，不能保证外部调用恰好一次；费用不确定的任务单独暂停，避免重复收费。参考 PostgreSQL 官方 [任务并发领取语义](https://www.postgresql.org/docs/current/sql-select.html)与 [pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html)。

### 24.2 TikHub 已核验的文档契约

以下结论来自公开文档，尚非真实响应验收；不能把文档示例作为线上 fixture。

| 来源 | 官方文档与接口 | 已知字段 / 限制 | Folio 接入判定 |
|---|---|---|---|
| 微信公众号文章 | [文章详情 V2](https://docs.tikhub.io/472974851e0)；`POST /api/v1/wechat_mp/v2/fetch_article_detail` | JSON `{ "url": "…", "raw": false }`；支持短链与含 `__biz` 的长链；文档字段含 `data.url`、`data.content.title/author/nick_name/content_text/cdn_url/ori_create_time` | 可进入样本联调；HTML、正文图片顺序和全文完整性仍须实测，不凭 `cdn_url` 推断全部图片可用 |
| X / Twitter 单条内容 | [推文详情](https://docs.tikhub.io/191321709e0)；`GET /api/v1/twitter/web/fetch_tweet_detail?tweet_id=…` | 文档列出 `code/request_id/cache_url/data`；示例 `data: null`，不足以确认正文、长文、引用和媒体结构 | 先验证单条公开文本；thread 自动展开、长文和媒体不列为已支持 |
| 其他公开网页 | 本轮未核验到通用任意 URL 正文接口 | TikHub 平台目录不能证明任意网站可抽取 | 接收并保存 URL，显示“仅链接”，可打开原网页；不计入支持来源正文成功率 |

请求基址为 `https://api.tikhub.io`，使用服务端 Bearer token。微信文档标价 **$0.01/次**，建议等待至少 30 秒，并提示部分超时可能计费；[平台介绍](https://docs.tikhub.io/4579905m0)中的常见接口价格不能替代该端点价格。X 单价、账户套餐/限速/余额及当前实际结算需在联调时核对。公开 OpenAPI JSON 获取返回 403，本轮未据此臆造未公开字段。

成本基线：按上述微信端点价，1,000 次请求约 $10，10,000 次约 $100，仅为供应商采集费用，不含失败重试、对象存储、流量、服务器与 AI。批量预取、自动轮询和无上限重试不进入 MVP。账户余额告警、每日全局预算、单账号处理预算与人工恢复入口在 M1 前配置。

### 24.3 接收、解析与恢复契约

1. App/分享扩展只提交 URL 和幂等键。服务端先鉴权、归一化和去重，在事务提交后返回内容 ID 与“已接收”；用户无需等待 TikHub。数据库接收失败时不得显示保存成功。
2. 保留原始 URL；微信长链不得盲目删除身份参数。X 状态 ID 从白名单域名与 URL 路径解析。供应商 ID 使用字符串或 Go `json.Number`，避免大整数精度丢失。
3. worker 校验 HTTP 状态、供应商业务结果、请求来源 ID 与响应来源一致性，再映射 `SourceDocument`：来源、规范链接、外部 ID、标题、作者、发布时间、正文块、媒体及完整性状态。X 字段映射待真实样本确定。
4. 正文为空、仅标题、内容截断或媒体缺失时不标记“完整”。仅 URL、部分完成与失败保留原始资产；已经可读的旧版本在新版本校验成功前不替换。
5. 429 按供应商恢复时间退避；鉴权/余额错误暂停并告警。对于超时或断线且计费结果未知的请求，不盲目自动重放；保留 request ID（如有）和状态，通过供应商可核验结果或受预算限制的明确重试恢复。不能假定本地幂等键能使 TikHub 免费去重。
6. 第三方正文按不可信内容处理：去脚本和危险链接；下载媒体限制协议、大小、类型、重定向及内网地址。第三方正文不能改变采集或未来 AI 的系统指令。
7. 记录耗时、来源、业务错误、完整性、重试次数和实际成本；日志不写 API token、正文和用户笔记。供应商 `cache_url` 不是 Folio 持久化正文，也不直接暴露给客户端。

`CAPT-03` 样本验收最低集合：微信正常图文 10 篇（包含短/长链接与多图）、X 单条公开内容 10 条（包含中文/长文本/引用/媒体差异），另测删除或不可访问来源、无效 URL、重复提交、供应商超时/限流/余额不足与进程重启。错误可用故障注入测试，但须与真实供应商响应分开记录。保存脱敏 fixture、外部 ID、正文长度、图片数量与顺序、缺失项、耗时和成本；完整/部分/仅 URL 分别统计，达到第 13 节门槛后才宣布支持。

### 24.4 先确定的数据契约

`BASE-03` 定义 `accounts/sessions`、`articles`、不可变 `body_versions` 与 `body_blocks`、`highlights/notes`、`ingestion_jobs`、幂等记录和消费记录；表名为设计建议，迁移尚未创建。

- 所有内容访问以账号为边界；重复来源仅在账号内去重，不泄露其他账号是否已保存。
- 高亮保存正文版本、块 ID、选中文字、前后文和块内范围；约定范围的字符单位，明确 Swift UTF-16 与服务端索引转换。正文更新无法唯一重定位时保留摘录并标记位置变化，不能用旧绝对 offset 静默跳错。
- 笔记采用 revision 乐观并发控制；冲突保留用户输入并提示选择，不以最后写入直接覆盖未确认修改。阅读位置保存为正文版本与块位置。
- 删除立即使列表、搜索和引用不可见；撤销期与最终清理时间按数据策略配置，关联图片/任务清理和备份恢复不得复活已删除账号的数据。
- 搜索返回命中类型与定位信息。批量导出使用一致快照/明确截止版本，覆盖所有分页；导出文件是用户主动生成的产物，不作为客户端自动维护的内容数据库。
- M4 的 `ArticleAskSession` 限当前文章或选区，引用绑定正文版本/块；无需先建设跨资料库 RAG 或向量索引。
